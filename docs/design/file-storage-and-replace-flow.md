# 文件存储与附件替换流程设计

## 背景

系统支持为就诊记录上传附件，并支持对现有附件进行替换。如果替换流程顺序不当，容易出现数据库记录已更新但新文件未写入成功，或者旧文件已删但新文件还未落盘的中间失败状态。

## 目标

1. 保证附件替换过程尽量不丢数据。
2. 支持本地文件存储与 S3 兼容存储。
3. 将文件元数据与业务记录稳定关联。

## 当前方案

### 存储抽象

文件模块对存储实现进行抽象，当前支持：

- 本地文件存储
- S3 兼容对象存储

### 替换顺序

附件替换采用以下顺序：

1. 接收并校验新文件，为原件生成唯一存储键，并预登记到 SQLite 清理队列。
2. 将新文件写入目标存储。
3. 更新附件元数据。SQLite 触发器在同一个事务中取消新键的清理任务，并登记旧键的清理任务。
4. 后台检查剩余引用，再按附件的存储类型删除无引用原件。移除附件以及级联删除就诊或成员通过同一队列处理。

## 风险控制

- 写入或提交失败时，先前版本保持可读，未引用的新对象进入清理队列。进程中断留下的预登记任务在一小时宽限期后可被回收。
- 清理工作每五秒检查一次队列。存储删除失败时，保留任务供一分钟后重试。
- 当前实现针对 SQLite 单实例部署。迁移到多实例时需验证写入保护、任务调度与数据库触发器。
- 升级只处理新登记的清理任务。历史遗留的无记录文件单独盘点。
