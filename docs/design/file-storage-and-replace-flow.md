# 文件存储与附件替换流程设计

## 背景

系统支持为就诊记录上传附件，并支持对现有附件进行替换。如果替换流程顺序不当，容易出现数据库记录已更新但新文件未写入成功，或者旧文件已删但新文件还未落盘的中间失败状态。

## 目标

1. 保证附件替换过程尽量不丢数据。
2. 支持本地文件存储与 S3 兼容存储。
3. 将文件元数据与业务记录稳定关联。

## 当前方案

### 存储抽象

文件模块对存储实现进行抽象，当前支持：

- 本地文件存储
- S3 兼容对象存储

### 替换顺序

附件替换采用以下顺序：

1. 接收并校验新文件。
2. 将新文件写入目标存储。
3. 更新数据库中的附件元数据。
4. 尝试删除旧文件。

这一顺序的目标是优先保证“新文件可用 + 数据库记录可指向新文件”。

## 风险控制

- 如果旧文件删除失败，业务主流程不回滚到失败状态，但可能产生孤儿文件。
- 后续可以通过离线清理任务回收孤儿文件。
- 如果未来引入分布式存储与事务协调，需要重新评估文件写入与数据库更新之间的一致性策略。
